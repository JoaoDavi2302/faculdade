## Como escrever requisitos
Existem padrões para poder escrever e definir requisitos
- Requisitos funcionais -> O sistema deve + (verbo + objeto) + (comp. Agente/nulo - para quem fazer a aplicação) + (condição/nulo)  - Tudo que tem condição é *requisito não funcional*
- complemento e condição são sempre opcionais, sempre que houver uma condição é um requisito não funcional
Todavia ainda não está claro como deve ser feito

## Especificação detalhada dos requisitos
Fazer sempre após o levantamento dos principais requisitos dos sistemas para melhor compreendimento dos detalhes dos requisitos, compreender fluxos de eventos e outras proprieidades e uniformizar entendimento entre clientes, usuários e equipe de desenvolvimento. (importante pra krl)

- Requisitos não precisam ser especificados todos de uma vez
- Podem ser priorizados de forma técnica ou por demanda do usuario

cliente compra requisito funcional
#### Indentificador
RF01/RF02 - ou usar REQ 1
#### Nome e breve descrição
RF01 - O sistema deve cadastrar veículo
Breve descrição(finalidade) -> objetivo do requisito: Para as pessoas alugarem veículo
#### Ator
Quem é responsável por executar essa funcionalidade: Administrador
#### Prioridade
Essencial para gerenciar requisitos e montar iterações
- Essencial - Deve ter
- Importante - Não é tão relevante e não deve ser descartável
- Desejável - não é relevante
Prioridade: Importante

#### Requisitos não funcionais(não é obrigatório ser preenchido)
Os requisitos técnicos relacionadas a funcionalidade
Pode ser colocado o idnentificador se todas as funcionalidades implementarem junto
##### Pré condição e pós condição
O que deve ser feito antes e depois da realização do requisito
Pré condição: Estar logado como admin na plataforma WEB
Pós condição: Estoque populado do veículo

#### Fluxo de eventos básico ou principal
Representa como o usuario deve executar a funcionalidade dentro da aplicação
- algoritimo em linguagem natural

Fluxo principal = happy ending
fluxo alternativo = erros, opções, exceções
